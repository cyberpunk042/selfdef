# bootloader-password-detect

Verifies GRUB2 has a password directive configured to
require operator credentials before editing boot params at
the GRUB menu. Catches the physical-access attacker who
boots the host, hits `e` at the GRUB menu, edits the
kernel command line to `init=/bin/sh` (or `single`), and
bypasses every userspace defense — including PAM, sudo,
ssh-hardening, fail2ban, the entire selfdef stack.

## Why this matters

Every userspace defense assumes the kernel was booted from
an operator-controlled init system. GRUB at default
settings lets ANY person at the keyboard:

1. Hit `e` to edit the kernel command line.
2. Append `init=/bin/sh` (or remove the init= entirely +
   add `single` for distros that respect single-user-mode).
3. Boot → drop to a root shell with `/` read-only mounted.
4. `mount -o remount,rw /` → full host control, no
   credential needed.

This bypasses:
- selfdef's PAM stack (pam-faillock, pam-pwquality, nullok-disable)
- ssh-hardening / fail2ban-bridge (no SSH involved)
- sudo-tune (sudo not consulted)
- audit-rules (auditd not running yet)
- AppArmor / SELinux MAC (not yet loaded as enforcement)

The defense is mechanical: configure GRUB to require a
password before letting the user edit the boot line. The
password is hashed with PBKDF2-SHA512 (`grub2-mkpasswd-
pbkdf2`) and lives in `/etc/grub.d/40_custom` or
`01_users`, which `grub-mkconfig` bakes into `grub.cfg`.

Selfdef provides DETECTION here (not configuration —
generating GRUB passwords requires operator interaction at
`grub2-mkpasswd-pbkdf2` prompt). The operator runs the
password-set workflow once; this module verifies on every
boot that it stayed configured.

## Profiles

| Profile | Effect |
|---|---|
| `report` (default) | log findings; exit 0; operator-pull via journalctl |
| `enforce` | exit 1 if no password OR plaintext password → systemd unit failed → notifier engine |

## Severity ladder

| Condition | Severity | Event |
|---|---|---|
| Non-GRUB bootloader (no grub.cfg found) | `ok` | `no_grub` (other bootloaders out of scope) |
| password_pbkdf2 directive + set superusers | `ok` | `grub_password_pbkdf2` |
| password_pbkdf2 directive but no set superusers | `warn` | `grub_password_pbkdf2_no_superuser` (directive may be unreachable) |
| plaintext `password` directive (deprecated) | `warn` | `grub_password_plaintext` |
| no password directive at all | `alert` | `grub_no_password` (physical attacker can edit boot params) |

## Detection logic

Scans:

| File | Why |
|---|---|
| `/boot/grub/grub.cfg` | Debian/Ubuntu, generated by grub-mkconfig |
| `/boot/grub2/grub.cfg` | RHEL/Fedora, generated by grub2-mkconfig |
| `/boot/efi/EFI/<distro>/grub.cfg` | UEFI installations (multiple distro paths checked) |
| `/etc/grub.d/40_custom` | Operator-edited custom fragment (pulled into grub.cfg at next grub-mkconfig) |
| `/etc/grub.d/01_users` | Distro-default user-set fragment |

Looks for:
- `set superusers="..."` — declares the user-set entitled to edit
- `password_pbkdf2 <user> grub.pbkdf2.sha512...` — hashed password
- `password <user> <plain>` — deprecated plaintext (still works but logged in journal, swap, etc.)

## Cadence

| Trigger | Why |
|---|---|
| `OnBootSec=10min` | Catch a freshly-regenerated grub.cfg that lost the password directive (operator ran grub-mkconfig without the right 01_users include) |
| `OnCalendar=Sun *-*-* 07:00:00` | Catch operator edits since last week |
| `RandomizedDelaySec=15m` | Avoid timer-herd-collision |

## MITRE coverage

- **T1542** Pre-OS Boot — PRIMARY; this is exactly the
  pre-OS bypass class.
- **T1542.003** Bootkit — narrower; bootkits typically
  modify the boot chain itself, but the password-protected
  GRUB also defeats the EDIT-existing-kernel-cmdline
  attacker variant.
- **T1078** Valid Accounts — defender-side; GRUB password
  is one of the few non-userspace credential checks the
  host enforces.
- **T1200** Hardware Additions — narrowly mitigated;
  attacker who plugs in a USB keyboard at boot still hits
  the GRUB password prompt.
- **T1556** Modify Authentication Process — narrowly
  related; a properly-set GRUB password prevents the
  attacker from booting into a context where they could
  modify userspace PAM.

## Setting up GRUB password (operator one-time setup)

This module ONLY detects. To set the password (operator
work):

```bash
# 1. Generate PBKDF2-hashed password
sudo grub2-mkpasswd-pbkdf2   # or grub-mkpasswd-pbkdf2 on Debian/Ubuntu
# Enter password twice; output is "grub.pbkdf2.sha512.10000.<salt>.<hash>"

# 2. Add to /etc/grub.d/40_custom (operator-edited)
sudo tee -a /etc/grub.d/40_custom <<EOF

set superusers="operator"
password_pbkdf2 operator grub.pbkdf2.sha512.10000.<salt>.<hash>
EOF

# 3. Regenerate grub.cfg
# RHEL/Fedora/Rocky/Alma:
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
#   (UEFI hosts may need /boot/efi/EFI/<distro>/grub.cfg path)
# Debian/Ubuntu:
sudo update-grub
#   (which runs grub-mkconfig -o /boot/grub/grub.cfg)

# 4. Verify
sudo selfdefctl modules check bootloader-password-detect
# Expect: severity=ok event=grub_password_pbkdf2
```

## Operator workflow

```bash
# Inspect last scan
journalctl -t selfdef-bootloader-password -n 1 --no-pager

# On-demand re-check (after grub-mkconfig)
sudo systemctl start selfdef-bootloader-password.service

# Manual verification — what files were scanned + what was found
sudo grep -E '^\s*(password|password_pbkdf2|set superusers)' \
    /boot/grub*/grub.cfg /etc/grub.d/*

# Switch to enforce profile after operator confirms password is set
sudo sed -i 's/^profile.*/profile = "enforce"/' \
    /etc/selfdef/modules/bootloader-password-detect.toml
sudo selfdefctl modules apply bootloader-password-detect
```

## Caveats

- **Allows BOOT but not EDIT**: GRUB's default `unrestricted`
  flag on each menu entry means the password is required
  only for EDITING the kernel command line, not for
  booting the default entry. This is correct behavior for
  hosts that need to boot unattended — the defense is
  against the EDIT attack. Hosts that want to require a
  password for boot itself need extra `--users root` /
  remove-`unrestricted` configuration.
- **GRUB password storage is in /boot**, typically not
  encrypted. The hash is PBKDF2-SHA512 — slow to crack
  but not impossible. Combine with full-disk encryption
  for layered defense.
- **Non-GRUB bootloaders** (systemd-boot, rEFInd, LILO)
  are out of scope; this module returns `no_grub` event.
  Future modules can extend.
- **Container hosts / cloud VMs** typically have no
  console access — the GRUB menu is unreachable. This
  module is most relevant for physical hosts + VMs with
  serial/IPMI console access.
- **TPM-bound LUKS** decryption can be configured to
  release the disk key only after measured boot
  validates kernel cmdline — that's a stronger primitive
  but more involved to set up. GRUB password is the
  lightweight first defense.

## Coexistence

- **secure-boot-status**: complementary — secure-boot
  attests the boot chain SHIM/grubx64/kernel signatures;
  GRUB password defends the editable command line on top.
- **kernel-lockdown**: orthogonal — kernel-lockdown
  restricts what kernel can do after boot; GRUB password
  controls what kernel command line gets used at boot.
- **kdump-disable + coredumpd-redirect + swap-encryption-
  detect**: complementary at-rest data-leak defense
  layer.
- **acct-baseline + audit-rules**: complementary — after
  boot, those record user actions; GRUB password ensures
  the audit-system actually starts (an attacker who
  bypasses to single-user mode never starts auditd).
- **integrity-sentinel**: complementary; integrity-
  sentinel watches /boot/* for modification — pairs with
  this module's password presence check.
